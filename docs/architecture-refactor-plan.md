# 架構重構與程式碼風險處理計畫

2026-09-25。範圍是維持現有功能與畫面行為，處理架構盤點中的四個候選、已確認的抓取來源問題，以及檢查時暴露的測試、lint 和文件缺口。UI/UX 改版另行進行。

## 目前基準

- `npm run build` 通過。
- `npm test` 有 3 個測試，覆蓋三個 Netlify 入口不能接受請求傳入的 `base_url`；修正已獨立提交。
- 限定原始碼執行 ESLint 時有 14 個 errors、2 個 warnings；全域 `npm run lint` 還掃到 `.agents/skills`、`.claude/skills` 和 `.netlify` 產物。這些訊息目前不等於已確認的功能 bug。
- 抽卡規則和規劃執行流程尚無自動化回歸測試。`README.md` 與 `docs/planner-core/README.md` 有舊路徑或舊技術棧敘述。

## 不變條件與驗收方式

重構每一步都要維持同一 seed、卡池、目標與資源下的抽卡位置、換軌、保底、好康轉蛋階段、成本排序、結果內容，以及取消和返回行為。以小型固定 `TrackGraph` 和代表性操作序列建立可重跑的基準；先記錄現有輸出，再在不改變預期結果的前提下逐步移動實作。

每個階段結束都執行：該階段測試、完整 `npm test`、`npm run build`、限定原始碼的 lint。最後另做桌面與手機寬度的實際操作檢查；這是功能確認，不調整視覺設計。新測試要跨使用者或呼叫端會用到的 interface 驗證行為，避免只複製實作判斷。

## 執行順序

### 0. 建立可驗證的基準

1. 已將抓取來源修正、三個入口回歸測試與 `npm test` 指令獨立提交，並將測試所用的 `esbuild` 列為直接開發依賴。
2. 限制 ESLint 的掃描範圍為 `src`、`shared`、`netlify/functions`、測試與設定檔，排除生成物及個人 skill 目錄。逐項記錄仍在原始碼中的 lint 問題；不以一個大量格式改動掩蓋行為變化。
3. 建立固定圖資料與「單抽、重複貓換軌、A/B 軌保底、十連第 11 抽、好康 3→5→7、資源不足、多卡池」案例。規劃與模擬皆使用這些案例，記錄目前輸出、位置和資源變化。
4. 建立規劃執行的控制式測試：慢回應後重跑、取消後回應、Worker 失敗、切回輸入頁。確認舊回應不可覆蓋新結果。

**完成條件：** 上述案例在改動前可重複執行；三個抓取來源測試、build 均通過；lint 只報專案原始碼的問題。

### 1. 集中抽卡規則（最高優先）

涉及 `src/features/planner/logic/core.ts`、`src/features/simulator/simulator.ts`、`src/features/track-graph/step-up.ts`。先盤出兩邊對單抽、十連、保底、換軌與好康階段的共同不變條件；如現有行為不同，先用基準案例判定應保留哪個行為，將實際 bug 與純重構分開記錄。

按「單抽與換軌 → 十連與保底 → 好康 3/5/7」的順序，讓規劃與模擬跨同一 seam 使用狀態轉移規則。規劃器保留搜尋、成本與剪枝；模擬器保留操作序列和呈現資料。每移動一種規則，就刪除相應的重複實作並跑雙方一致性測試，避免增加一個只轉送呼叫的淺 module。

**完成條件：** 同一圖、起點、前一隻貓與操作序列在兩個呼叫端產生相同抽卡與游標結果；既有規劃成本和步驟不變。

### 2. 集中一次規劃的執行流程

涉及 `PlannerPageContainer.tsx`、`useTrackGraphs.ts`、`usePlannerWorker.ts` 及相關 context。先用階段 0 的控制式測試固定取消、過期回應和結果快照行為。再把抓圖、Worker 執行、取消與錯誤處理移入一個較深的執行 module；頁面只負責草稿、畫面階段和使用者動作。移除唯一呼叫端不用的 `useTrackGraphs` 狀態 interface，並讓 token/seq/abort 的有效性判斷集中在同一處。

分開處理瀏覽器 history 與結果 stage，保留返回鍵現有語意。每次移動一段流程就驗證重跑、取消、失敗、成功與返回；不要一次重寫四個 context。

**完成條件：** 快速連續執行或取消後，舊請求與舊 Worker 結果不能覆蓋最新狀態；成功結果仍對應執行當下的輸入快照。

### 3. 集中卡池資料取得規則

涉及 `useEventCats.ts`、`useTrackGraphs.ts`、三個 Netlify 入口與 `_lib`。以固定 HTML fixture 驗證活動、貓咪與軌道圖解析結果。將重複的 event metadata 組裝、來源選擇和請求參數規則集中到同一 seam；各端點保留各自解析及回應內容。抓取來源一律採部署設定；對可重試狀態、timeout 與錯誤回應作明確驗證。

只合併確實重複的規則。不為統一三段 JSON 輸出而額外建立薄轉送 module，也不更改目前遠端資料來源。

**完成條件：** 三個入口的回應形狀、快取語意與解析結果維持一致；請求無法覆寫後端抓取來源；fixture 與入口測試通過。

### 4. 深化結果資料 module

涉及 `logic/view-model.ts` 與 `components/ResultTable.tsx`。先比較桌面表格和手機卡片在分組、展開十連、步驟排序、資源總結上的共同資料不變條件。只有確實相同且重複的資料推導才移入既有 `buildDrawRows` 所在的 module；展開互動或呈現細節繼續留在各自的畫面 module。

用同一 `PlanResult` 驗證桌面與手機看到的步驟、抽數、命中與成本相同；另外檢查展開/收合與回到輸入頁。此階段不改版面或樣式。

**完成條件：** 兩種呈現的資料一致，且資料規則不再由兩處各自推導；使用者操作和畫面內容維持原樣。

### 5. 清理剩餘風險並封版

逐項處理原始碼 lint：`any` 改為窄化的 `unknown` 或正確型別、刪除未用值、確認 `useEventCats` 的 effect 依賴、檢查 bottom-sheet effect 的動畫與關閉時序。每一項若牽涉可觀察行為，先建立能重現問題的測試；未能重現的提示只做最小、可審查的修正。修正 `README.md` 與 `docs/planner-core/README.md` 的舊技術棧、路徑和失效連結。

最後執行完整測試、build、專案範圍 lint，並以固定案例在桌面與手機寬度手動跑一次主要流程。列出仍未確認的風險，不把 lint 警告直接宣稱為已修復的 bug。

## 依賴與變更切分

`0 → 1 → 2 → 3 → 4 → 5` 是建議順序。第 3 階段可在第 1 階段測試基準建立後獨立推進；第 4 階段依賴第 1、2 階段輸出資料穩定。每個編號內再以一種規則或一種流程為單位提交，讓每次變更都可單獨檢查與回退。確認有行為差異時，先記錄重現案例與預期，再以獨立修 bug 變更處理。
